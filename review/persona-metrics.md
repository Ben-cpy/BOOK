# 独立试用：会看指标，但容易误判因果

## 结论

2026-11-08，在独立空项目中完成两轮试用、共 **7 次真实 Codex CLI 用户输入、2 个会话**。本场景通过：模型没有因为自己讲过一遍、用户换话题、用户作出错误归因或仅说结束语，就写入掌握记录；直到用户正确应用概念并继续设计实验，才更新地图。更新由真实 Stop Hook 保存；7 次都没有向用户报告内部地图维护。第二轮还验证了新会话只凭已存地图就能接上已知知识。

这是 Agent 扮演用户的合成试用，不是真实用户验收，也不改变 `vllm-kv-oneshots.md` 的待审批状态。未观察到本场景需要单独修复的问题。

## 五轮实际体验

### 第 1 轮：还没理解

用户：

> 我在接手一个推理服务的性能实验。我会看毫秒数，但 TTFT、TPOT 和 prefill、decode 老是混在一起。为什么前缀缓存命中了，总响应变快，后续生成每个 token 却可能没变快？请用一小段通俗的因果解释。

回答用“先读题，再逐字作答”连接两个阶段，解释复用输入计算可以减少起步等待，而后续逐 token 速度未必变化。关键句：

> 起步等待少了，即使后续速度相同，总响应时间也能缩短（在输出长度相同的情况下）。

地图保持空。模型没有把这段自己的解释立即记为用户已掌握。

### 第 2 轮：直接换话题

用户：

> 先停一下性能分析。之后这些实验的原始 trace 和整理后的表格，你建议放在项目里的什么目录？只建议目录结构，不用创建文件。

回答给出按实验和运行组织的 `raw/`、`tables/`、`metadata/` 目录。地图仍为空，也没有创建用户未要求的目录。这轮刻意检查“停止追问 ≠ 已经理解”。

### 第 3 轮：应用错了

用户：

> 回到这组实验：开 APC 后 TTFT 从 800ms 变 200ms，TPOT 仍是 25ms，总耗时更短了。我打算在结论里写“APC 加速了 decode，所以输出更快”。这个说法可以吗？

回答直接纠正：

> 这组数据表明首个 token 出得更早，没有显示 decode 加速。

随后用“少等 600ms、后续每 token 仍是 25ms”解释总耗时为何减少，并提供可用的报告措辞。地图依然为空：没有保存错误归因，也没有把刚发生的纠正当作掌握证据。

### 第 4 轮：正确应用并继续任务

用户：

> 我把结论改成“主要节省了命中前缀的输入处理时间，首 token 更早到；后续逐 token 生成没有明显变化”。这轮并发设为 1，确认没有排队。接下来我会保持输出长度一样，对比短公共前缀和长公共前缀；若长前缀那组 TTFT 降得更多，是否更支持这个解释？

回答直接进入实验设计：比较各自开启与关闭 APC 的 TTFT 差值，控制硬件和后缀长度，确认命中并重复测量；没有重新讲 prefill/decode 的定义。

这一轮模型首次写候选。Stop 保存后的实际文件是：

```markdown
# 已掌握

## 推理性能实验
- 前缀缓存复用输入处理与首 token 提前的因果关系
- 首 token 等待时间与后续逐 token 生成耗时的区别
- 排队与输出长度对性能对比的影响
```

三个节点是知识边界，没有把本次数据、完整解释或对话原文塞入地图。

### 第 5 轮：继续产出报告

用户：

> 继续这组结果：短公共前缀的 TTFT 从 100ms 到 90ms，长公共前缀从 800ms 到 200ms，输出都是 100 token，TPOT 都在 25ms 左右。我的报告先画 TTFT 的对比图，并把 TPOT 单列为没有明显改善。给我一句可以放在图下的结论，不需要再解释指标定义。

完整回答只有一句：

> 在并发为 1、无排队且输出均为 100 token 的条件下，APC 使短、长公共前缀的 TTFT 分别降低 10% 和 75%，而 TPOT 均维持在约 25ms，支持其收益主要来自前缀输入处理的复用，且长前缀收益更明显。

地图与第 4 轮完全相同，无候选、无新增维护消息。

## Round 2：新会话遇到反直觉结果，再只说结束语

第二轮沿用同一项目已自然形成的三节点地图，**开启全新会话，不恢复上一段对话**。会话 ID：`01a1baf2-9c48-7ed1-8bf4-54d340320eb8`。测试输入不含“省讲”、地图内容或前次解释。

### 第 6 次输入：命中多了，性能反而变差

用户完整输入：

> 现在实验里缓存命中更多，但 TTFT 反而变差了，这是我之前把前缀缓存理解错了吗？

模型没有重新定义 prefill/decode，也没有认定用户丧失了原有理解。回答先补充边界：“前缀缓存减少的是输入处理的计算量，不保证整体 TTFT 一定下降。”紧接着明确连接已有认知：

> 你已经知道排队会影响首 token 时间。把它和缓存放在一起，可以粗略拆成：
>
> TTFT ≈ 排队时间 + 缓存查找／读取等开销 + 未命中部分的输入处理 + 首 token 生成时间

这句话有明确来源：新会话的用户输入没有提到排队知识，而注入地图包含“排队与输出长度对性能对比的影响”。它是模型使用地图的直接行为证据，比同一会话里没有重复定义更有说服力。

模型用“省下 20ms，但排队或读取增加 40ms”说明抵消关系，再区分四类原因：命中请求数与命中长度不同、总输入增长使剩余计算反而增加、缓存可能存在读取/搬运成本、实验负载可能不同。最后问“命中更多”具体是什么口径。它既保留上层理解，也补充了当前问题真正缺少的因果连接。

**地图没有变化。** 这些刚解释的更深原因都没有立即被记录为掌握。

这两次输入新增 2 次 UserPromptSubmit 和 2 次 Stop：均退出 0，Stop 返回 `{}`，调用前后地图字节一致，无候选写入。结合第一轮，总计 14 次真实 Hook。第二轮完成后 `.know/pending/` 仍为空。原始证据增加 `turn-6.jsonl`、`turn-7.jsonl` 和对应 `summary.json`。

## 这次试用没有证明什么

- 第 5 轮明确要求省讲定义，同一会话也保留前文，因此不能把那次简洁回答全部归因于地图。Round 2 已补测跨会话使用，但没有做同问题“有地图/无地图”的随机对照。
- 只完成两组短对话，没有形成稳定成功率或模型间比较。
- 判断“排队与输出长度对性能对比的影响”是否过宽，仍属于语义判断；本次用户确实主动控制了这两个变量，但代码无法保证标签总是恰当。
- 没有测试用户真实认知变化；测试验证的是 Agent 在给定对话证据下的行为。
