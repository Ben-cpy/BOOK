# 独立试用：懂基础、追问细节、纠正误判

## 结论

第一轮五次真实 Codex 交互中，地图的增、留、删均符合本场景预期：追问更细内容时保留已有知识；正确应用后才增加子节点；用户承认“只是背了那句话”时，只撤回对应的过宽记录。正常保存和不更新都没有向用户宣布地图维护。

主要不足是解释成本：纠正机制误解时，模型已经用三步说清因果链，仍继续附箭头图、矩阵公式和重复总结。对于“懂一点但不多”的用户，可以明显压短。这是产品体验问题，格式校验器不会发现。

这份记录是**合成用户角色驱动的真实 Codex 会话**，不是人工用户验收。原行为案例仍待用户审批。

## 方法与边界

- Windows，Codex CLI 0.164.0，Python 3.9；模型继承本机配置，测试驱动设置推理强度 `low`。
- 独立临时 Git 项目，从只有 `# 已掌握` 的空地图开始，没有预填示例。
- 五轮均通过 `codex exec` / `exec resume`，同一个真实会话。问题不提 Skill、地图或预期记忆内容。
- 观测包装器把原始事件交给实际 `hook.py`，原样返回其输出；仅额外记录地图前后值。
- 测试使用已审阅命令的单次 Hook 信任绕过选项。此场景没有验证交互式 `/hooks` 信任操作。
- 同一对话里的解释省略，不能单独证明模型在没有对话历史的新会话中利用地图；第二轮还明确要求不要重讲 prefill/decode。因此本报告不把它作为跨会话效果证据。

## 五轮发生了什么

| 轮次 | 用户的实际行为 | 回答与地图的实际结果 | 判断 |
|---|---|---|---|
| 1 | 正确说明固定文档在前、变化问题在后；知道前缀复用主要减少 prefill。随后问 35-token 前缀、16-token 块的尾部怎么处理 | 解释当前请求正常用尾部 KV、跨请求只命中 32；地图只记已展示的三条基础，未记新讲的块边界 | 通过 |
| 2 | 继续追问：末尾 3 个也是算过的，不能复用是原理限制还是实现粒度？ | 说明模型原理允许复用，但完整块缓存没有部分命中路径；地图完全不变 | 通过 |
| 3 | 把实验表修成命中 32、剩 3 计入 prefill，并推导 48 的理论上限 | 新增完整块粒度及两个子节点，保留已有基础 | 通过 |
| 4 | 承认此前“KV 依赖前文”只是背诵，实际上还以为 KV 只由 token 和位置决定 | 仅删除过宽的 `KV 依赖前置上下文`；保留请求布局、完整块子树、prefill/decode；解释机制但没有立即重新记为掌握 | 地图通过；回答偏长 |
| 5 | 据解释设计“前缀同长度不同内容”的反例和“相同前缀”的正例，要求写成两行实验项 | 正常完成两行任务；增加更窄的上下文条件节点及子节点，没有记录用户未展示掌握的矩阵运算或层间传播细节 | 通过 |

第 4 轮完整问题：

> 有一处我得纠正自己：开头我说“KV 依赖前文”，其实只是记住了这句话，脑子里一直把 KV 当成“token 加位置编号”算出来的。我会按固定前缀排请求，也会按完整块算命中，但机制上并没想通：把前面的提示换成同样 token 数的另一句话，文档 token 和位置都一样，KV 为什么还会变？

回答的关键因果链是正确的：第一层的同一 token KV 可以相同，但注意力会读到不同的前文；这改变第一层输出，后续层据此生成的 KV 就可能改变。回答随后又用箭头图、公式、文字总结重复同一关系，存在压缩空间。

## 尚不能由本场景推出的结论

第一轮只是一条五轮对话，没有估计不同模型、措辞或长对话下的误判率。用户的正确应用表达得比较明确；含糊的“嗯”“知道了”需要其他角色单独验证。地图的语义粒度仍由模型决定，当前条目可读，但未必是用户最偏好的组织方式。

## 第二轮：压缩解释后的真实复测

针对上述体验问题，主 Agent 在 Skill 中加了一条窄规则：先用简短、完整的通俗解释补上因果链；公式或更底层机制按需；避免列表、图、公式重复表达同一条因果。

重新创建空地图项目 `%TEMP%/cognition-depth-7gkuk5q_`，真实执行原第 1 轮问题，再执行完全相同的第 4 轮纠错问题。会话为 `01a1baf4-ff2e-7601-9818-b0d06a33e3c7`。同名 `.prompt.txt`、`.jsonl`、`.map.md` 和 Hook 观测文件保留在该项目。

| 对比项 | 修复前 | 修复后 |
|---|---|---|
| 最终回答字符数，含 Markdown、换行与公式 | 809 | 598，减少约 26% |
| 表达方式 | 三步说明，再重复箭头图、公式及总结 | 三步文字说明，无公式或重复箭头图 |
| 因果完整性 | 注意力读到不同前文 → 上层输出表示变化 → 后层 KV 可能改变 | 同一条因果链完整保留，并解释第一层 KV 不会被反向改写 |
| 地图修正 | 撤回“KV 依赖前文”的过宽判断 | 同样撤回该机制记录，保留请求布局和 prefill/decode；接受用户明确陈述的完整块计算能力 |
| Hook 行为 | 正常注入、候选写入、Stop 保存 | 两轮均正常注入和 Stop 保存，无格式重试 |

复测说明窄修复能减少这次回答的冗余，未通过省略必要因果来缩短。598 字符仍比“几句话”长，对类似问题还可以更紧凑；不能据此宣布解释长度已经稳定。两组前置对话长度不同、各只采样一次，这不是严格受控的效果统计。

## 第三轮：更明确的简洁偏好仍非硬保证

主 Agent 将规则进一步收紧为：优先用一段、几句话串起“原因 → 中间变化 → 结果”，在用户所问深度结束；保留按需展开的空间。再次在独立空地图项目 `%TEMP%/cognition-depth-yxue0ehc` 中重放原第 1 轮和原第 4 轮问题，**没有在用户问题中额外要求简短**。会话为 `01a1baf9-044d-7071-89b3-3ce3cdae7b58`。

同一纠错问题的最终回答变为 **500 字符、11 行**。相对第二轮减少约 16%，相对最初减少约 38%。因果链仍完整：前一层注意力读取的前文变化，改变文档 token 的输出表示，后一层据此生成的 KV 随之可能变化；同 token、同位置不足以保证整套 KV 相同。回答没有公式和重复箭头图。

但结果仍是“开场 + 三步列表 + 两段总结”，**没有稳定收敛成一段几句话**。这说明指令能改善冗余，却不能保证每次都达到用户偏好的解释长度。对此保留为实际限制，不再为单个例子继续叠加规则。

两次 UserPromptSubmit 与两次 Stop 均成功，地图只保留已展示或明确陈述的请求布局、prefill/decode 和完整块计算能力，撤回“KV 对前文上下文的依赖”这一过宽机制判断；无格式重试，完成后 pending 无残留。本角色三轮合计 **9 次真实 Codex 交互**。
