# vLLM KV cache · 行为案例

以下为合成的待审批案例，用于检查解释和地图更新是否符合预期。

## A · 没懂时，把因果链讲清楚

用户反复问「开头换了，后面的文档一样，为什么不能接着复用？」

**合适的回答**：两次请求可以写成 A → 文档和 B → 文档。自回归模型处理文档中的位置时会看到之前的 token。A 换成 B 后，文档虽然字面相同，后续层的 KV 仍可能不同。所以 vLLM 标准 APC 把上游前缀计入块身份，分叉后的文档需要重新计算。

**地图变化**：这个问题仍在追问时，暂不加入已掌握树。如果原树把这一项写得过宽，缩小或移除对应条目。

**反例**：只回答「块身份包含上游前缀」，或回答完立刻记为已掌握。

## B · 同类任务继续推进，可以默认已经理解

解释过命中对输入处理的影响后，用户继续审阅同组 TTFT 与 TPOT，后续相关交流没有再卡在两者区别上。

**合适的行为**：直接给实验数据，默认这部分可以省讲，并在前缀复用下面写「前缀命中与首 token 延迟的关系」。

**反例**：要求用户复述才能写入，或者每次都重复 prefill/decode 的定义。

## C · 向下探索，掌握后再把树写深

原地图已经包含：

```markdown
# 已掌握

## KV cache
- 前缀复用
  - 相同文本在不同前文下的 KV 可能不同
```

用户问「前缀一致我懂了，文档结尾只填半个块呢？」

**合适的回答**：按标准 vLLM V1 APC 路径，当前请求可以使用已算出的半块 KV。跨请求命中按完整块计算，这半块尚不能独立作为完整块命中。

后续讨论表明这一层也理解后，在父节点下加「完整块与部分块的复用边界」。

**反例**：因为问了更细的问题就删掉已掌握的父节点，或者把新问题直接当成已掌握。

## D · 换话题，保留现有记录

解释完前缀命中后，用户改问「下一份实验 trace 放哪里？」

**合适的行为**：回答文件组织问题。仅凭这次话题切换，无法判断前缀机制是否已经理解，地图无需更新。

**反例**：把停止追问直接当作新增掌握记录的唯一依据。
